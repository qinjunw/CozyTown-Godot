# 预算账本锁检查验证

对应[修复预算锁竞争时的账本缺失误报](https://github.com/qinjunw/CozyTown-Godot/issues/41)。修复提交 `93f6ea946ad9113aeee1b9f89e7e1d66ee8e2c24` 基于 `4eda1e7f9ab6096cbfaccaf202ac82843fa73044`。本记录使用合成账本和真实 OS 文件锁，不访问现实账本、凭据或模型服务。

## 已观察问题与修复

[模型回放绑定修复](https://github.com/qinjunw/CozyTown-Godot/issues/40)在 `c8255f50937cf0b38c3224f5039fea69aa3b0b65` 的 Model 全套回归为 82／83，通过数以外的一例是 `manual-original/full-demo-v1`：子进程退出码为 `[11,0]`，输出 `ledger_missing`，预期为 `[10,0]`。随后一次两配置定向诊断为 1／2，同一配置报同一错误。原始 TRX 和日志保留，不改写为通过。

当时 `AcquireLock` 在尝试取得持久 `.lock` 独占锁之前检查 live 账本。确定状态重现由外部写入者持有真实独占锁，并把合成 live 文件暂移到替换位置；读者分别调用公开 `OpenExisting` 或 `Reserve`。三份注册配置的六例均在锁释放前错误返回 `ledger_missing`。这证明未持锁的存在性检查会误判该替换状态；原失败是否恰好由 `File.Replace` 的具体 OS 窗口触发仍是推断，测试没有捕获该窗口。

修复把已有锁标记时的 live 存在性检查移到取得独占锁之后，再验证标记和读取账本；检查异常释放已取得的锁。没有锁标记时继续区分从未创建的账本与丢失标记。费用、并发、阶段、恢复身份、停止、写入替换和未知占用规则不变。

## 红绿与公共回归

| 检查 | 结果 |
| --- | --- |
| 持锁替换状态红阶段：首切片／v1／v2，各打开与准入 | 6／6 失败，均记录 `ledger_missing` |
| 同一状态修复后 | 6／6 通过；等待锁，live 恢复后继续；原未知费用和槽位保留 |
| 真正缺失回归及上述六例 | 9／9 通过；锁释放后缺失仍拒绝，previous 字节不变，异常后锁可立即重新取得 |
| 原跨进程失利的一次定向复核 | v1／v2 2／2 通过；一笔已有占用后仅一个新请求获准，另一个明确 `concurrency_limit`，退出码 `[0,10]` |
| 单次 Model 全套 | 92／92 通过，失败和跳过为零 |
| 新测试补充 `using` 兜底清理后的定向检查 | 9／9 通过；生产代码未改变 |

测试使用 .NET SDK 10.0.401、Debug；首次恢复启用 `-p:RestoreLockedMode=true`，其后使用 `--no-restore`。新测试在读者开始后观察 200 毫秒持锁状态，再恢复文件或释放锁；操作完成等待上限为 5 秒。这里的文件移位是显式合成的存储状态，不依赖碰巧发生短暂替换窗口。

Model 全套保留初始化竞争／中断、真正缺失、锁标记错配、坏 JSON、三份配置隔离、两个物理槽、费用与阶段上限、未知占用、恢复至多一次，以及占额进程终止后的重新打开。原失败仅作一次专门复核，随后运行一次完整回归；没有循环重跑直到成功。
